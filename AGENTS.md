# Project guidance

## Keeping this file current

- Whenever a task reveals a new project, build, emulator, rendering, integration, or workflow fact, update this file during the same task before handing off.
- Include the operational consequence, command or invariant when useful, and keep the guidance concise and actionable.

## Builds

- This repository builds the Luped CGM watchface, the standalone Loop/Trio face (variant `luped`, the default), and Luped Remote (variant `lupedhelper`, `build/luped-remote.pbw`, UUID `738255f4-b58b-41cd-a7ae-27fc80e81fcb`), a watchapp built from the same `main.js.in` under the `helper` flag (every variant's `watchface-config.json` must list `helper`, as the assembler throws on a flag missing from a config). CrimsonBear, which Luped was split from, lives in `dabear/CrimsonBearPebbleWatchFace`.
- Luped Remote must never change Luped's build: put helper code only inside `// @if helper` sections (`// @if helper` / `// @else` / `// @endif` where it replaces Luped code), and after any change rebuild `--variant luped` and compare its build-time-neutral PBW hash and assembled `main.js` with the previous build. `scripts/test-*.cjs` assemble with a non-nesting regex, so never nest `// @if` sections. The helper's own minify allowlist is `extra_private_methods` (`helper*` methods) in its `build-release.sh` case.
- Use `PEBBLE_BIN="$(command -v pebble)" ./scripts/build-release.sh [--variant <variant>] --build --minify` for release verification.
- Luped has no archive-size guard: its stub gives XS 52 KB from the app heap, so its limit is the XS memory measured with `--install --measure-memory` (below). Report Alloy size, PBW size, and SHA-256 from the build summary. The build summary also shows the XS machine the C stub asks for and every module in the archive (flagging ones the watchface does not import); `--install --measure-memory` (with `--phone` default or `--cloudpebble`) then restarts the watchface with logs on and reports slot, chunk and stack use against what is available and the app heap left for PebbleOS. Report those too, and flag anything at or above 85% (slots, chunks) or under 12 KB of free app heap.
- Every module the manifest matches goes into the Alloy archive, imported or not. Moddable's `manifest_typings.json` (editor type-checking only) matches the SDK typings folder's `tsconfig.es2024.json`, `tsconfig.es2025.json` and `package.json`, about 2.8 KB of dead modules, and `"*": "./*"` compiles every staged file. Luped's manifest leaves the typings include out and its stage leaves out `protocol.js` (Luped 0.1.9 went from 31,615 to 28,089 Alloy bytes, 4,044 B headroom). Check `build/variants/<variant>/project/build/mods/emery/mcrun/tmp/pebble/release/embeddedjs/files/*.xsb` to see what is in the archive.
- The archive still costs app heap about byte for byte: in the emery emulator, Luped Remote's free app heap went from 12,756 to 18,368 B when its Alloy archive shrank by 5,327 B, and an unminified build (+2,435 B) lost 2,948 B. Keep code that a variant never runs inside `// @if` sections.
- The real limit is XS runtime memory, not the archive size. By default an Alloy app runs in a fixed 32 KB static block (stack 384 slots, slot heap from 512 slots, chunk heap from 8 KB, both growing inside the block); when it fills, the app dies with "Alloy: Fatal Error / memory full". Luped measured on a Pebble Time 2 (PebbleOS 4.41.2) with that block: slot heap ~94% and chunk heap ~87% used. `ModdableCreationRecord` in the C stub can set `stack`, `slot` and `chunk` (bytes); above 32 KB in total the firmware allocates them from the app heap instead (PebbleOS 4.21+, #1621). Luped's own stub (`variants/luped/src/c/mdbl.c`) asks for 4 KB stack, 32 KB slots and 16 KB chunks: slots ~50%, chunks ~41%, 28.7 KB of app heap left for PebbleOS; 64 KB in total also ran with 16.4 KB left.
- To measure XS memory, build with `--measure-memory` (it defines `LUPED_XS_INSTRUMENTATION`, which sets `kModdableCreationFlagLogInstrumentation` in the creation record). Never ship it: the firmware keeps the flag only when app logging is on as the app starts, but then samples every second for the whole run, also after logging is turned off, which most likely cost Luped 0.1.11–0.1.20 about a third of the watch's battery life. With a log listener connected the firmware logs `instruments:` once a second (App bytes free, Chunk used/available, Slot used/available, Stack used/available, GCs, Keys used, …). `pebble install --logs` misses the startup lines; subscribe to app logs first and restart the app from `pebble repl`.
- An Alloy watchface's "Fatal Error" dialog stays above everything (even after deleting the app or launching another watchface) until a button is pressed on the watch.
- When bumping a variant, raise the version in `variants/<variant>/package.json`.
- Build both `emery` and `gabbro`; a successful build of only one platform is not sufficient.
- Builds are reproducible except for build time and the checkout path: `pebble-app.bin` carries the build time (offset 0x7C) and a GNU build ID (offset 0x94, 20 bytes) hashed over debug info that includes the absolute stage path, plus a header CRC (0x14) over both; `manifest.json` carries timestamps and CRCs. The same sources built in a different checkout directory therefore differ in those bytes only.
- Pebble Tool requires Python 3.10 on Apple Silicon (`uv tool install --python 3.10 pebble-tool`).
- pebble-tool runs waf with the SDK's own `SDKs/<version>/.venv/bin/python` but passes its own `sys.path` as `PYTHONPATH`, so the SDK venv must use the same Python minor version as pebble-tool. A mismatch fails right after the Moddable prebuild with `AssertionError: SRE module mismatch`. Fix it by recreating `.venv` with pebble-tool's Python and `pip install -r sdk-core/requirements.txt`, or by reinstalling the SDK.
- In this workspace, the verified fallback Pebble Tool executable is `/private/tmp/cgm-pebble-venv/bin/pebble` (Pebble Tool 5.0.40, active SDK v4.33.1); set `PEBBLE_BIN` to this path when `pebble` is not on `PATH`.
- The macOS emulator also requires Homebrew `libpng`.
- Relative to v4.36.1, PebbleOS v4.36.2 is an alarm-only patch: it re-picks one-time alarm days at boot and fires alarms missed by up to five minutes while the watch was down. Relative to v4.36.0 it also includes v4.36.1's one-line change disabling resume for the native-heartbeat analytics logging session. None of these releases changes Alloy, Moddable, app memory, resource loading, AppMessage, or rendering.
- Release-build delays can come almost entirely from npm: the wrapper runs `npm ci`, and `pebble build` performs additional staged dependency checks. Warm-cache installs may finish in under a second, while a registry/cache validation can stall for about five minutes; Emery/Gabbro compilation itself typically takes under a second.
- Use `--skip-deps` for repeated local builds only after a successful dependency install. It requires `npm ls --all` to pass and the installed hidden lock to exactly match `package-lock.json`, then removes build-only dependencies from the isolated stage to prevent Pebble Tool's redundant install. It is rejected for publishing.

## Variant boundaries

- Variant selection happens while assembling `src/embeddedjs/main.js.in`; keep variant-only drawing and behavior inside `// @if <flag>` sections (`// @else` and nesting are allowed; marker lines are dropped).
- Keep constants used only by variant-gated code inside the same `// @if` section; otherwise generated variants can fail lint with unused bindings.
- Each variant has its own UUID (Luped's differs from CrimsonBear's), so they can coexist on a watch. When emulator results look like the wrong face, reset the disposable emulator state and install the intended PBW alone.
- Luped has no PebbleKit JS companion (`enableMultiJS: false`). CLI AppMessage injection does not reliably reproduce its Loop integration.
- Loop (`LoopWorkspaces/LoopWorkspaceNextDevCriticalAlerts/Loop`, `LUPED_PEBBLE` flag) pushes to Luped through its own CoreBluetooth PPoGATT server, side by side with the Pebble app. The transport and Luped logic live in the `dabear/elbbepTransport` Swift package (`~/Code/elbbepTransport`: `ElbbepTransport` generic PPoGATT/AppMessage link, `LupedKit` payload, alarms/mute, delivery, status and log; `swift test`), which Loop links as a remote package on branch `main`; Loop's `LupedPebbleTransport.swift` is only an adapter. After pushing the package, move the `elbbeptransport` pin in `LoopWorkspace.xcworkspace/xcshareddata/swiftpm/Package.resolved` and re-resolve, or Loop keeps building the old commit. Changes to the `DATA` protocol must update `LupedKit` and `variants/luped/PROTOCOL.md` together. The legacy PebbleKit iOS binary never detects Core watches: its discovery validates advertisement manufacturer data, and Core watches use company ID `0x0EEA` with new hardware platforms. PebbleOS opens a separate app session for any phone PPoGATT service whose meta names a non-system app UUID.
- PebbleOS routes outbound AppMessages (and inbound-message ACKs) from apps with JS enabled to the Pebble app's system session (`comm_session_get_current_app_session`). CrimsonBear (`enableMultiJS: true`) can therefore receive pushes from a third-party app session but cannot ACK them or send refresh requests to it; only JS-free faces such as Luped get a two-way Loop session.
- Alloy watchfaces send AppMessage key 15025 (`kPKJSReadyMessage`) at startup and keep `Message` unwritable until the phone sends any message back, so a third-party phone transport must answer that handshake before Luped's `COMMAND: "refresh"` arrives. Without the session capability `AppMessage8kSupport` (from the phone-version reply on endpoint 0x11), PebbleOS limits a JS-free face's inbox to 144 bytes; the capability is cached per app UUID and applies on the face's next start. For screenshots, a temporary source-level sample state may be used, but restore all production defaults and rebuild the final artifact afterward.
- For mmol/L visual fixtures, use mmol/L thresholds (for example urgent-low 3.0, low 4.0, high 10.0). Reusing mg/dL thresholds makes normal readings appear in the low color.

## Luped Remote (watchapp)

- Buttons: JS imports `pebble/button` (Moddable's Pebble module, `toolchain/moddable/build/devices/pebble/modules/button`); the host blocks it in watchfaces only, so no C forwarding is needed. `new Button({ types: [...], single: { repeat }, onPush(pushed, button, recognizer, count, repeat) })` subscribes the top window's click handlers; subscribing `back` overrides the system Back, so the app calls `watch.exit()` itself on Back from its main screen.
- Confirmation chord: a second `Button` with `raw: true` on up/down (the top and bottom right buttons; Select is not part of it) gives press (`pushed` 1) and release (0) events, so `helperRaw` tracks which are held; once both went down within `CHORD_MS` (500 ms) on the confirm screen, a 100 ms interval fills a bar (repainting only that full-width strip) and sends after `HOLD_MS` (2 s) with a short buzz; releasing either first resets it. Select alone never sends. Time holds in the emulator with `pebble emu-button --duration <ms> click up down` (separate push/release commands add about 1 s of tool start-up). Back has no raw events (the module maps it to single clicks). The chord's own single clicks arrive on release and are ignored until 300 ms after both are up.
- Exit and auto-close: `watch.exit(reason)` sets the exit reason and pops all windows; `watch.exit(1)` (`APP_EXIT_ACTION_PERFORMED_SUCCESSFULLY`) returns to the watchface instead of the launcher. The remote closes after 60 s without a press (countdown and a shrinking bar in its header, reset by every press), and pauses the countdown while a request waits for `RESULT` (30 s timeout; at least 15 s are left afterwards to read the answer).
- The remote leaves out Luped's diagnostics, telemetry (`DIAGNOSTICS` key, `COMMAND diagnostics`), battery sampling, pop-up buzz matching and the `DATA` history (`@if helper` / `@else`); it keeps `countDiagnostic()` and `recordDraw()` as no-ops for shared code, and keeps the whole signed-bolus path. Measured in the emery emulator with one `DATA` message: 18,368 B app heap free at a 37,443 B Alloy archive, 151 keys, stack 2.5 of 4 KB (the sending and result screens then grew the archive to 40,395 B; not re-measured). Its XS slots (32 KB) and chunks (16 KB) are left as they are: post-GC use is ~22 KB slots and 8–11 KB chunks.
- Measure in the emulator by building the stage with `#define LUPED_XS_INSTRUMENTATION 1` prepended to `src/c/mdbl.c`, `pebble install --emulator emery`, and piping `APP=…; WAIT=20` plus `scripts/xs-usage.py` into `pebble repl --emulator emery`. A first run can print `XSUSAGE NONE`; run it again. Its `live_*` values are one sample after a collection and shift with GC timing between builds; the app-heap minimum and keys are stable. Its quick stop/start can leave the watchface it returns to "not responding" in the emulator.
- Quick Launch can't be set for the user: PebbleOS keeps it in watch prefs (`qlSingleClickUp`, `qlUp`, … in `fw/shell/normal/prefs.c`), which apps have no API for and the phone can only write through BlobDB (endpoint 0xB1DB, `private`: the Pebble app's session only). The README and store description tell users to pick **Settings → Quick Launch → Tap Up → Luped Remote** (Tap Up defaults to Health; Tap Down, Hold Up/Down/Center/Back and the Back+Up and Up+Down combos also exist). The AppRunState endpoint 0x0034 is `any`, so a third-party phone session such as Loop's could start the remote by UUID (not built).
- Settings persist with the `localStorage` global (Moddable `WebStorage` over key-value storage, per app UUID). They survive reinstalls in the emulator; `pebble wipe` resets them.
- In the emulator, redrawing the whole screen every second while buttons were pressed quickly made the app vanish without a log or an exit call (XS memory stayed below its limits; it survived 150 presses with no second ticks). The tick now repaints only the header (`helperDrawHeader`), and 180 rapid presses ran clean. Not yet checked on a watch.
- Luped's write-failure path (close and reopen `Message`) only runs after the first `DATA`; without a host for this UUID the emulator shows `Sent …, waiting`, then `<action>: not sent` after 30 s.
- Use the same temporary source-level sample state as Luped for screenshots, and remove it before the final build.
- Remote actions need a phone connection (`isConnected`): without one the list dims them (Settings stays usable), Select on one only double-buzzes, and a send whose connection dropped on the confirm screen ends as `<action>:not sent, no phone`.
- After the hold, the remote shows a Sending screen with a wheel (a 100 ms interval repaints only its strip), then a Done/Not done screen when `RESULT` arrives or the 30 s wait times out, with the existing short/double buzz. Back hides the wheel; Select or Back closes the answer.
- Remote buzzes: short when a request is actually sent (not on a refusal, whose double buzz would be dropped by PebbleOS), long when the phone answers `ok`, double otherwise; no stale-data buzz (the watchface gives that). A new reading doesn't clear the remote's answer (Luped's does). `helperResultText()` maps Loop's `signedbolus`/`signedforcedbolus` answers to Bolus and the outcomes (`ok`, `refused`, `ignored`, `failed`, `no key`) to words. Bolus is dimmed without the phone's `auth:v1` key and opening it shows "Not done: Phone doesn't allow it". The bolus and carbs confirm screens show glucose and IOB, and any confirm shows "No recent CGM data" in red when the reading is stale.
- `demoTestOnly` (every variant's config lists it; publishing refuses it) builds a test version that needs no phone: sample `DATA` and a test bolus key arrive at startup, the phone always counts as connected, and each request gets `<action>:ok` after 3 s instead of being sent (`signedbolus:ok` for a bolus, as Loop answers). Set it to true in `variants/lupedhelper/watchface-config.json` only for the build, then back to false. Its status line reads "Connected to test data".
- `pebble emu-bt-connection --connected no` doesn't reach the app (no `connected` event, the status stays connected); to test the disconnected state, call `setPhoneConnected(false)` from a temporary fixture.

## Rendering invariants

- The footer owns cached state for clock, date, battery, and Bluetooth independently.
- Clock, date, and battery comparisons happen only from `minutechange`, using `event.date`; redraw only the region whose value changed.
- Connection changes redraw only the Bluetooth indicator region. Do not clear or redraw unrelated footer fields.
- The CGM reading timestamp is absolute local `HH:mm`, not relative age, and is updated only by a CGM/content render—not by the footer minute render.
- Treat the initial phone configuration state as unknown. Show the neutral connecting screen during the first handshake, and show setup instructions only after an explicit `CONFIGURED: 0` response.
- Graph mode follows the CGM Skyline hierarchy: bold glucose centered in the ring, a smaller delta below it, and a narrow reading-time strip rendered behind the lower part of the ring.
- Full-screen mode has no reading-time strip. Put the reading time inside the ring below the delta, and make the ring meet the footer without a gap.
- Once a configured face has rendered, preserve the pale content background and fixed status-strip fill during content updates; clear/redraw only the changing timestamp and dynamic ring/graph pixels. Initial setup, resize, and fullscreen/layout transitions still require the static layers.
- In graph mode, the trend arrow sits outside the ring's radius, so the ring/backdrop redraw never repaints that spot. Explicitly clear its bounding box (see `arrowClearRadius` in `face()`) before drawing, or a direction change leaves the old glyph's strokes mixed with the new one. Full-screen mode doesn't need this: its arrow sits inside the ring, which the inner white circle already repaints every render.

## Emulator verification

- Verify both graph and full-screen modes for each variant after layout changes.
- Capture Emery screenshots with `pebble screenshot --emulator emery --no-open <path>` and inspect the actual image, not only build success.
- The first frame immediately after install can be blank or show setup while the coalesced render or first phone handshake is pending. Capture again after the app settles before diagnosing a rendering failure.
- Open each requested screenshot automatically on macOS after capture.
- Never leave sample glucose data, forced `configured`, forced `fullScreen`, or diagnostic rendering changes in production source.

## CloudPebble and emulator operations

- CloudPebble installation requires `pebble login` first; the login flow authenticates through Firebase/GitHub and may open a browser.
- Install a phone build with `pebble install build/luped-cgm.pbw --cloudpebble`. Confirm the proxy authenticates, the phone connects, and `App install succeeded` appears.
- Different watchfaces (each variant, CrimsonBear) use different UUIDs. Installing one does not reliably make it the active emulator watchface when another is already running; use `pebble wipe` (without `--emulator`) and `pebble kill`, then install the intended PBW alone for unambiguous screenshots.
- `pebble wipe` has no `--emulator` option; it resets the current disposable emulator state. Do not use `--everything` unless account data and all SDK-version state may be removed.
- After installing or injecting data, wait for the app’s coalesced render before capturing. A setup, blank, or stale frame immediately after the command can be transient.
- When a screenshot is requested, save it under `assets/`, open it with macOS `open`, and inspect the image contents before reporting visual verification.
- For Luped, the CLI cannot reliably inject named AppMessage fields because it has no PebbleKit JS companion. Use a temporary source-level sample state only for visual checks, then restore defaults and rebuild the production PBW.
- For refreshed visual assets, use the in-range mmol/L fixture (6.8 glucose, +0.2 delta, 5.4–6.8 readings, thresholds 3.0/4.0/10.0), isolate it from the companion with `SCREENSHOT_FIXTURE`, and use `--vnc` when the emulator must remain available for a separate screenshot command. Restore the fixture and rebuild production artifacts before publishing.

## Pixel-budget reporting

- The diagnostics `invalidatedPixels` counter reports transaction area, not individual drawing writes. For a typical 24-hour estimate, use 1 initial full frame, 288 CGM updates (5-minute cadence), and 1,440 minute events; add one 58×30 date region redraw and any actual battery/Bluetooth changes.
- The clock minute redraw clears a dynamic, center-aligned region sized to `max(previous, current clock width) + 2` (mirroring the battery clear), with the width cached in `footerState.clockWidth` and seeded by `footer()`. A previously fixed 86×30 box left artifacts because the proportional `Bitham-Black` clock can render wider than 86px, so a narrower new value failed to clear the old glyph's outer edges. Region height stays 30; minified and unminified builds have identical pixel geometry. Emery’s content-only region is 200×198 and Gabbro’s is 260×230. The fixed pixel-redraw table's clock row still assumes 86×30 and must be recomputed on the next release build now that the clear width is dynamic.
- User-facing platform names are Pebble Time 2 (`emery`, 200×228) and Pebble Round 2 (`gabbro`, 260×260); use those names in reports instead of only the platform codenames.
- Rendering uses a single-flight gate (`renderBusy`) with dirty/priority flags and zero-delay event-loop coalescing. The gate is cleared in `finally`, and queued work is serviced afterward; render-failure retries preserve their longer delay. A lock alone would drop updates or cause redundant retries.
- `Battery` is sampled at most every `BATTERY_SAMPLE_INTERVAL_MS` (5 minutes) from the existing minute wake-up, not on every `minutechange`. Hourly diagnostics are marked pending (`telemetryPending`/`telemetryDueAt`) and ride the next outbound write (a refresh request or `onWritable` flush) instead of forcing their own; `DIAGNOSTICS_PIGGYBACK_GRACE_MS` (15 minutes) forces a dedicated flush only if nothing else has sent them by then. On-demand `COMMAND diagnostics` requests from the phone still flush immediately via `requestDiagnostics()`.
- Explicitly call `flushOutbound()` after assigning a newly constructed `Message`; its initial `onWritable` callback can run synchronously before `this.message` receives the instance and otherwise strand the startup request.
- `Message.onWritable` indicates send availability, not confirmed phone delivery; `onSuspend` can also mean temporary outbox contention (see the official Alloy App Messages guide). SDK 4.33.1 routes send failures through the same reactivation path as successful sends. Run `npm test` (`scripts/test-luped-signing.cjs` for the signed bolus MAC, `scripts/test-luped-warnings.cjs` for the host-app-change and newer-protocol warnings).
- Minute events render with zero delay, so the minute tick and its redraw share one wake-up; do not reintroduce a fixed delay (the former 400 ms added a second timer wake-up every minute).
- Remaining battery opportunity: splitting CGM content into smaller dirty regions where Poco layering permits. The zero-delay coalescer minimizes latency; a short 25–75 ms coalescing window is an optional burst-energy tradeoff.
- After every release build, recompute and report the fixed daily pixel-redraw table below for both platforms (full frame + 288 CGM updates + 1,440 minute clock redraws + 1 date-rollover redraw; battery/Bluetooth redraws stay out of the fixed total since they're variable), diff it against the "Last recorded" table, call out any change (or state explicitly that there is none), and overwrite the "Last recorded" table with the new numbers and date/commit.

- Keep exactly two screenshot assets per variant: normal graph mode and fullscreen mode. `--publish` uploads `assets/emery_luped_{graph,fullscreen}_screenshot.png` (Luped) with `--replace-screenshots`.
- Each variant publishes with `./scripts/build-release.sh --variant <variant> --publish`. Publishing refuses to run while `allowShakeDebugActionTestOnly` is on, and also creates a GitHub release `<variant>-v<version>` with the PBW (needs `gh`); raise the version in the variant's package.json first, as an existing tag stops it. The script also passes `--description` and store icons, which pebble-tool uses only when it creates a missing store listing (matched by UUID); edit existing listings on the RePebble dashboard. Luped's store description must state that it needs a direct connection from a supported iPhone app such as Loop or Trio.
- The `/private/tmp/cgm-pebble-venv` fallback can lose its `pebble_tool` sources to temp cleanup (`ModuleNotFoundError: No module named 'pebble_tool'`). Recreate a Python 3.10 venv and `pip install pebble-tool==5.0.40` instead of reusing it.
- RePebble rejects publishing a release version that already exists; screenshot-only store updates require a new patch version before retrying publication.
- Alloy's `Message` (SDK `pebble-appmessage.c`, `commSessionEvent`) runs `updateActive(is_open && is_system && pkjsReady)` on every comm-session event, so a third-party app session opening or closing (e.g. Loop restarting or reconnecting) makes a JS-free face's outbox unwritable until the face restarts; only a system-session open or the face's first received message re-enables it. Inbound pushes are unaffected. Luped's startup refresh still works, but later watch-to-phone messages (diagnostics replies) need a watchface restart. The upstream fix is to ignore non-system session events.
- Luped `DATA` index 9 is an alarm bitmask (1 urgent low, 2 low, 4 high) and index 14 is the urgent-low repeat in minutes; both are read by the watchface. Loop sends its active glucose alert profile: thresholds, per-zone switches, and repeat intervals (1,440 minutes when Loop alerts once per episode).
- Loop owns all watch-alarm mute state: with **Follow Loop Alert Mute** (default on, `lupedPebbleFollowAlertMute`), Loop sends `DATA` index 9 as `0` while its alerts are muted and resends the profile mask when the mute ends or is cancelled. Luped has no mute field or timer. Luped's no-recent-data (stale) buzz ignores the mask and always fires once when the reading becomes 15 minutes old; Loop's communication log records each change in the watch-alarm reason.
- Luped alarm palette is variant-specific: low glucose uses red (`low`), high glucose uses yellow (`high`), and both the ring and glucose value obtain their color from the shared `glucoseColor()` path.
- Luped rings are solid: normal glucose uses the shared green `accent`, low uses red (`low`), and high uses yellow (`high`) through `glucoseColor()`. Do not add gradient or shading arcs.
- Emery/Gabbro are 6-bit color (2 bits per RGB channel: hardware quantizes every channel into 4 bins — 0–63, 64–127, 128–191, 192–255 — truncated to 0/85/170/255). Screenshot colors won't match source RGB values; use `pebble screenshot --no-correction` for the raw quantized framebuffer when verifying exact colors, since the default color-corrected output remaps them. This also caps how many visually distinct tones a gradient can show — more than 2–3 interpolated steps between close colors usually collapses back to the same 1–2 quantized buckets.
